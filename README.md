# Meridian Line Predictor

A single-page Next.js app that predicts train arrivals for a fictional commuter line ("Meridian Line") using a statistical model driven by historical delay patterns, real live weather, and mock track/train incidents.

There is no real transit agency behind this — the schedule, stations, and incidents are all fictional/mock data. The one real external input is live weather, pulled from [Open-Meteo](https://open-meteo.com/) (no API key required).

## Getting started

Node and npm are installed via `nvm`, so in a fresh shell run:

```bash
source ~/.nvm/nvm.sh
npm install   # only needed once, or after pulling dependency changes
npm run dev
```

Then open [http://localhost:3000](http://localhost:3000).

Other commands:

```bash
npm run build   # production build (also runs the TypeScript check)
npm run lint    # ESLint
npm run start   # serve a production build
```

There is no test suite.

## What it does

- **Arrivals board** — pick one of the 6 stations and see the next several trains, each with a scheduled time, an AI-predicted time, a delay status, and a plain-English reason for any delay.
- **Conditions banner** — current weather at the line's location, plus a live count of active incidents.
- **Incident panel** — report a track-damage, train-fault, or congestion incident (or remove one), and watch it immediately affect predictions for trains that cross it.
- **Live map** — a schematic (not geographic) SVG diagram of the line showing station order, live train positions, flagged segments, and faulted trains.

## How predictions are made

Prediction is a deterministic statistical model, not an LLM call. For a given train arriving at a given station, the predicted delay is the sum of:

1. **Historical baseline** — a small hand-authored table of average delay by time-of-day bucket (early-morning / peak / midday / evening / night), each with a plausible cause (`src/lib/historicalDelays.ts`).
2. **Weather** — real current conditions from Open-Meteo, mapped from the WMO weather code (plus precipitation/wind) to a delay-minutes contribution, capped at 12 minutes (`src/lib/weather.ts`). If the weather fetch fails, this contribution is simply dropped — the UI shows "Weather unavailable" rather than breaking.
3. **Incidents** — any active track-damage/congestion incident on the segment the train is approaching the station from, or any train-fault incident targeting that specific train, each adding minutes based on severity (minor/moderate/severe) (`src/lib/incidents.ts`).
4. **Live drift** — a small, deterministic sine-wave jitter (seeded by train + station) so the displayed prediction shifts slightly between polls, without being random or requiring any stored history (`src/lib/predict.ts`).

The delay **minutes** sum all four factors. The displayed **reason** string only names the single dominant cause, in priority order: incident > weather > historical baseline.

## Mock data model

- **Line**: 6 stations, Westbrook Terminal → Ashford Junction → Central Crossing → Lakeview → Brookfield → Highland Park Terminal, fixed travel times between each adjacent pair.
- **Schedule**: for each direction, trains are generated by walking a virtual clock from 05:00 to midnight, spacing departures by the current time bucket's headway (e.g. every 12 minutes at peak, every 45 minutes overnight). This produces roughly 120 trains a day, entirely programmatically — no trip is hand-written.
- **Incidents**: a new baseline set (0–3 incidents) is deterministically generated each calendar day from a seeded random sequence, so it's stable within a day but varies day to day. Manually added incidents persist alongside the baseline until removed.

**Incident state lives in memory on the server process** — it resets whenever the dev server restarts and is not shared across multiple server instances. This is intentional for a project of this scope; there is no database.

## Project structure

```
src/
  app/
    page.tsx                  Server Component shell — renders <TrainTrackerApp/>, no data fetching
    layout.tsx, globals.css    root layout + theme variables (light/dark via prefers-color-scheme)
    api/
      weather/route.ts         GET — proxies Open-Meteo, 10 min revalidate, graceful failure
      incidents/route.ts       GET/POST — list / create incidents
      incidents/[id]/route.ts  DELETE — remove an incident
  components/                  TrainTrackerApp + ConditionsBanner, StationSelector, ArrivalsBoard,
                                DelayBadge, IncidentPanel, LineMap (each with a .module.css)
  lib/
    types.ts                   shared types
    schedule.ts                stations, schedule generation, upcoming/active-train queries, map position math
    historicalDelays.ts        the one hand-authored delay-by-time-of-day table
    random.ts                  dependency-free seeded RNG (FNV-1a + mulberry32)
    weather.ts                 Open-Meteo request building + weather-code → delay mapping
    incidents.ts                in-memory incident store, baseline generation, validation
    predict.ts                  combines all factors into a PredictionResult
```

Schedule generation and the prediction formula are plain, pure TypeScript functions with no I/O — they run directly in the browser (imported into client components), so only weather and incidents require a network round-trip.

## Notes on scope

- `LINE_COORDINATES` in `src/lib/weather.ts` is a placeholder lat/lon used only to query weather for "the line's region" — it isn't tied to a real place. Swap it for a real location if you want.
- No authentication, database, or deployment config — out of scope for this project.
- `cacheComponents` is left disabled in `next.config.ts` (Next's classic caching model); see `CLAUDE.md` for why that matters if you're touching the API routes.
