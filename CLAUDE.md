## What this is

A single-page Next.js app: an AI-assisted arrival predictor for a fictional commuter line ("Meridian Line", 6 stations, `EB`/`WB` directions). All schedule data is generated programmatically — nothing is hand-authored per-trip. "AI" here means a deterministic in-app statistical model, not an LLM call. Delay predictions combine:

1. A hand-authored historical delay table by time-of-day bucket (`src/lib/historicalDelays.ts`).
2. Real live weather from Open-Meteo (no API key), fetched server-side.
3. Mock incidents (track damage, train faults, congestion) — a daily auto-generated baseline plus manually added ones via a form in the UI, all backed by an in-memory server-side store.
4. A small deterministic sine-wave "jitter" so predictions drift slightly between polls without being random or requiring stored history.


## Architecture

**Everything is derived from pure functions in `src/lib/`, imported directly by client components — there is no client/server data-fetching layer for the schedule or prediction math itself:**

- `schedule.ts` — station list (`STATIONS`, fixed order/index), segment travel times, and `generateDaySchedule()` which walks a virtual clock from 05:00–24:00 per direction, using the current time bucket's headway (from `historicalDelays.ts`) to space out departures and build each train's full stop sequence. Also exports `getUpcomingStops`, `getActiveTrains`, `getTrainPosition` (interpolates a train's position along the line for the SVG map, based on **scheduled** times), and `isAdjacentSegment`.
- `historicalDelays.ts` — the one hand-authored table (delay averages + causes per time-of-day bucket), plus `getTimeBucket(date)`.
- `random.ts` — dependency-free seeded RNG (FNV-1a hash + mulberry32). Used for (a) a stateless sine-based "drift" in predictions, keyed by `(trainId, stationId)` so it's deterministic but changes as `now` advances, and (b) day-seeded baseline incident generation, so the same calendar day always produces the same baseline incidents.
- `predict.ts` — `predictArrival(train, stationId, now, weather, incidents)`: sums historical + weather + incident-severity minutes + jitter into a delay, but the **reason string** picks only the single dominant cause (incident > weather > historical) — see the precedence comment in that file before changing it.
- `weather.ts` — Open-Meteo URL building and WMO weather-code → delay-minutes mapping. `LINE_COORDINATES` is a placeholder lat/lon (documented in-file as swappable); it is not a real location.
- `incidents.ts` — the in-memory incident store (module-scope array, **resets on dev-server restart, not multi-instance-safe** — intentional, no database in scope). `ensureBaselineForToday` regenerates the seeded baseline when the calendar day rolls over while preserving manually-added incidents. Validation lives here (`addIncident` throws `IncidentValidationError`, caught in the route handler and turned into a 400).

**Route handlers** (`src/app/api/`) only exist where server-side I/O or shared mutable state is required — weather (external fetch, `next: { revalidate: 600 }`, always returns HTTP 200 even on upstream failure so the UI can degrade gracefully to "weather unavailable") and incidents (GET/POST/DELETE against the in-memory store). Everything else (schedule generation, prediction math, map position math) runs client-side with no network round-trip.

**Component tree** (`src/components/`): `TrainTrackerApp` (`'use client'`) owns all state — `trains` (computed once via `useMemo`), `now` (ticks every 20s), `weather`, `incidents`, `selectedStationId` — and passes it down to `ConditionsBanner`, `StationSelector`, `ArrivalsBoard` (+ `DelayBadge`), `IncidentPanel`, and `LineMap` (inline SVG, schematic not geographic). `src/app/page.tsx` is a Server Component that renders only static shell content — it does no data fetching, so there's no SSR/hydration mismatch risk from time-based state.

**Caching model**: `cacheComponents` is intentionally left disabled in `next.config.ts` (classic model). Route Handlers are dynamic by default in Next 15+; the weather route's own `fetch` call controls caching via `next: { revalidate }`. Don't reach for `use cache`/Suspense-for-dynamic-data patterns here — they're a different (opt-in) model this app doesn't use.

Next.js 16 ships `AGENTS.md` (auto-regenerated by `next dev`, referenced above) warning that this version has breaking changes vs. older training data — check `node_modules/next/dist/docs/` before relying on remembered App Router APIs, particularly around Route Handler `params` typing (`Promise<{...}>`) and the Cache Components model.
